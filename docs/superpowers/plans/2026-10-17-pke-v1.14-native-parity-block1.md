# PKE Beat Battle V1.14 Native Parity — Block 1 Implementation Plan

## Goal

Reproduce the current PKE Beat Battle V1.14 experience for Block 1 in the native C++ build without redesigning it.

Block 1 covers:

- Home / Title
- Halloween event shell and state
- real 15,000-player background population simulation
- Practice selection
- Practice gameplay
- Practice result
- save/restore continuity across all of the above

The implementation technology changes, but the visible game and behavior should remain V1.14-compatible.

## Source priority

When references disagree, use this order:

1. V1.14 executable behavior and data
2. V1.12 embedded HTML/CSS/JavaScript
3. previous design docs and handoff notes
4. reconstruction or assumptions only as a last resort

## Global constraints

- No WebView2, Chromium, DOM, Canvas, Web Audio, IndexedDB, or browser-owned application timers.
- C++/SDL2 owns rendering, input, audio, gameplay, files, save data, and scene lifecycle.
- QuickJS is used only for browser-independent compatibility logic where retaining the original JavaScript reduces parity risk.
- The UI uses 1280×720 logical coordinates with uniform letterboxing/pillarboxing.
- The registered population is 15,000 from startup.
- Population state continues while the player is on Home, Halloween, Practice, Gameplay, and Result screens.
- Practice must never change Online RP or normal Online W/L/D.
- V1.14 save data used for migration is read-only and must not be modified or deleted.
- No disk I/O in note-judgement or audio hot paths.
- Do not copy all 15,000 player records from JavaScript to C++ every rendered frame.
- Halloween Auto mode uses Oct 15 00:00 JST through Nov 1 00:00 JST, with Force On / Force Off retained.
- V1.14 values override older V1.12 values, including the 255,000 Halloween TEAM threshold where applicable.

## Implementation tasks

### Task 1 — Track the canonical Native source directly

- Materialize and verify the canonical Native source tree against the current baseline.
- Keep the existing source bundles only as historical transfer artifacts.
- Update Windows CI so it builds tracked source directly instead of reconstructing product source during every build.
- Run existing offline tests before any behavior changes.
- Verify the Windows Release package still contains no WebView2/Chromium runtime files.

Completion check: existing Native tests and Windows package build pass before the parity work begins.

### Task 2 — Add an isolated QuickJS runtime

Create a small C++ wrapper with operations equivalent to:

- initialize runtime/context with memory and stack limits
- evaluate bundled JavaScript source
- call a named compatibility function with JSON input/output
- collect garbage explicitly when appropriate
- report JavaScript errors and stacks to Native diagnostics

The JavaScript runtime must not receive DOM, Canvas, Web Audio, direct filesystem access, or browser storage APIs.

Tests must cover:

- basic JSON round-trip
- browser globals being absent
- JavaScript exception capture
- memory/stack-limit failure without crashing the process

### Task 3 — Import V1.12 Block-1 logic and V1.14 corrections

Import only the browser-independent parts needed by Block 1, including population, title calculations, song-difficulty helpers, and required dependencies.

Keep the original calculation order and random-number call order wherever practical.

Expose a small compatibility surface equivalent to:

- initialize
- advance to time
- get population summary
- serialize population state
- restore population state

Create deterministic fixtures using a fixed clock and seeded test-only randomness for:

- startup
- one-minute advancement
- rest/sleep transitions
- serialization/restore equivalence
- Halloween start/end boundaries
- registered population 15,000
- V1.14-specific value overrides

### Task 4 — Build the nonblocking PopulationRuntime

Run QuickJS on one dedicated background thread.

The main/render/gameplay thread must only submit the latest target time and read the most recent immutable summary.

The runtime must:

- coalesce repeated time updates
- never queue one expensive population job per rendered frame
- never move simulated time backwards
- catch up correctly after large elapsed-time gaps
- keep the last known-good summary after a JavaScript error
- refuse to checkpoint a failed/corrupted generation

Tests must include the accepted continuity example:

Home 60 seconds → Gameplay 180 seconds → Result 30 seconds = exactly 270 seconds of population progression.

### Task 5 — Add safe Native persistence

Use the existing normalized Native player save and add a dedicated population-state file.

Writes follow:

1. write temporary file
2. close/flush it
3. parse and validate the serialized data
4. replace the durable file only after validation succeeds

Tests must cover:

- missing save
- valid save
- malformed save
- malformed temporary file
- interrupted replacement
- write failure
- legacy V1.14 migration source remaining byte-identical

### Task 6 — Build cached asset catalog and song difficulty parity

Centralize Songs and Characters discovery in `AssetService`.

Requirements:

- cache metadata instead of reparsing every frame or keypress
- one corrupt Song/Character does not invalidate the whole catalog
- Practice gets display name, difficulties, star ratings, icon metadata, and paths from the catalog
- star calculation follows the reference implementation exactly

Only change the existing ChartParser or CharacterLoader when a focused parity test proves a mismatch.

### Task 7 — Move all UI to V1.14 1280×720 logical coordinates

Replace the current prototype 1920×1080 presentation assumption with the V1.14 1280×720 design space.

Required viewport cases:

- 1280×720 → 1:1
- 1920×1080 → 1.5×
- 1280×1024 → centered 1280×720 with 152px top/bottom bars
- 2560×1080 → centered 1920×1080 viewport with 320px side bars

Mouse/input hit-testing must use the same transform as drawing.

Text and image textures should be cached so unchanged UI text is not recreated every frame.

### Task 8 — Implement Halloween state and overlay

Implement exact JST event boundaries and Developer override behavior.

Use V1.14 as authority for:

- Candy state
- four shop skins
- shop costs/unlock rules
- 5000-Candy `トリックオアビート!` title behavior
- other Block-1 event UI values

Do not guess any value that cannot be confirmed from the reference.

Shop/History-heavy content should be built or refreshed only when opened, not on every Home update.

### Task 9 — Implement V1.14 Home

Use V1.12 HTML/CSS for concrete geometry/style values and V1.14 visible behavior as the final authority.

Reproduce:

- logo/header area
- REGISTERED / ONLINE / LIVE / WAIT counters
- animated selected-skin preview
- player/status area
- song and character counts
- existing Home button positions
- Halloween entry

Later-block buttons stay visible in their normal V1.14 positions but do not transition yet.

Do not add Native-only `COMING SOON` labels or redesign disabled buttons.

Startup order:

legacy migration → Native save load → population restore/start → asset catalog refresh → Home.

### Task 10 — Implement V1.14 Practice selection

Reproduce the existing Practice flow:

- player side selection
- search
- star filter
- song list
- mouse navigation
- keyboard navigation
- Enter to play
- Escape/back behavior

Filtering must operate on cached metadata, not re-read all files repeatedly.

Launching gameplay must not pause background population progression.

### Task 11 — Match V1.14 Practice gameplay logic

Build deterministic reference cases for:

- SICK / GOOD / BAD / MISS timing
- combo
- score
- accuracy
- HP changes
- miss deadlines
- sustain hit/break/completion
- ghost taps
- opponent notes
- song completion

Write a focused failing test before changing each behavior that differs from V1.14.

The existing Native gameplay engine is a foundation, not the authority.

Practice results must never update Online RP or normal W/L/D.

### Task 12 — Match V1.14 gameplay rendering and character behavior

Capture reference geometry for:

- receptors
- note movement
- sustain rendering
- HP bar and HUD
- score/accuracy display
- judgement popup
- BF/DAD positions
- character scale/flip
- Sparrow XML frame offsets
- idle/sing animation timing

Use deterministic rendering tests at fixed song times.

Renderer remains presentation-only and must not own gameplay state.

### Task 13 — Implement Practice Result and full Block-1 flow

Reproduce the V1.14 Practice Result presentation and controls.

Required route:

Home → Practice → Gameplay → Result → Practice → Home

Also support replay according to V1.14 behavior.

Add safe checkpoint/flush points after appropriate completion/event operations and on shutdown.

Shutdown order:

1. final population advance
2. capture last known-good checkpoint
3. durable save flush
4. stop QuickJS population worker
5. destroy gameplay/audio
6. destroy SDL resources

### Task 14 — Add visual and performance parity gates

Reference states to capture at 1280×720:

- normal Home
- Halloween Home
- Halloween overlay / Shop
- Practice
- gameplay idle
- gameplay note hit
- gameplay sustain
- Result

Image comparison should be strict for layout, geometry, colors, and artwork. A narrow tolerance is allowed only for font rasterization/antialiasing differences.

Performance tests must verify:

- `PopulationRuntime::AdvanceTo()` is nonblocking from the gameplay thread
- snapshots do not contain the full 15,000-player graph
- worker tick durations are recorded for diagnostics
- no disk I/O is introduced into gameplay/audio hot paths

### Task 15 — Harden Windows CI and final acceptance

Windows CI must run the full test suite before packaging.

The final package must include required Native compatibility scripts/assets and exclude test/reference-only fixtures.

Automated acceptance checks include:

- registered population = 15,000
- Home → Practice → Gameplay → Result → Home flow
- 4m30s population continuity test
- RP/W/L/D unchanged by Practice
- population state survives restart
- legacy source save unchanged
- Halloween boundary/override behavior
- no WebView2/Chromium runtime

Real Windows-device smoke test includes:

- Home
- Halloween
- Practice search/filter
- complete one song
- Result
- return Home
- F11 fullscreen
- resize/letterbox mouse input
- clean exit
- relaunch/restore
- diagnostics check for periodic population-induced gameplay stalls

## Completion rule

Block 1 is complete only after:

- offline core tests pass
- dependency-enabled full tests pass
- Windows Release x64 build passes
- package verification passes
- visual/golden/end-to-end/performance parity gates pass
- forbidden-browser-runtime scan passes
- GitHub Actions artifact upload succeeds
- Windows real-device smoke test passes

Only renderer-level micro-differences such as unavoidable font antialiasing may remain. Gameplay, state, save, event, population, or layout differences from V1.14 are not accepted completion differences.
