# PKE Beat Battle V1.14 Native Parity — Block 1 Design

Date: 2026-10-17
Repository: `cubesugar310/PKE-Native-Build`
Status: Approved design; implementation has not started

## 1. Goal

Port the current PKE Beat Battle V1.14 experience to a genuine Windows-native implementation without redesigning the game.

The target experience is: a V1.14 player should launch the Native build and find the same PKE Beat Battle, with the major implementation difference being that WebView2/browser rendering is gone.

Native-only UI cleanup, layout redesign, simplified placeholder systems, fake population values, or speculative feature changes are out of scope.

## 2. Source-of-truth order

When references disagree, use this order:

1. V1.14 executable behavior and data.
2. V1.12 embedded HTML/CSS/JavaScript as the primary implementation reference when V1.14 source is unavailable.
3. Existing design docs, handoff notes, and historical specifications.
4. Reconstruction or assumptions only as a last resort.

The supplied V1.12 package is `PKE_Beat_Battle_DISTRIBUTION_HALLOWEEN_EVENT_V1_12_BACKGROUND_GC_HOTFIX.zip`.

V1.12 code is a reference, not an authority over V1.14. If a value or behavior changed by V1.14, the Native implementation follows V1.14.

## 3. Project decomposition

The full Native parity effort is split into blocks so each one can be specified, tested, and completed without a giant partially-correct rewrite.

1. **Block 1:** Home + Halloween + 15,000-player population runtime + Practice + Gameplay + Result
2. Block 2: Ranking + Record + Titles + Player Progress
3. Block 3: Online Battle + Matchmaking + LIVE + Spectate
4. Block 4: Friends + Private Match
5. Block 5: Normal Boss + Halloween Boss
6. Block 6: Replay + Settings + Discord Presence + remaining parity details

This specification covers Block 1 only.

The split does not permit throwaway foundations. Population state, save state, event state, asset loading, and bridge contracts created in Block 1 must be usable by later blocks.

## 4. Existing Native foundation

The current Native C++/SDL2 implementation remains the base. Existing pieces include or partially include:

- C++20 application/runtime
- SDL2 windowing/rendering/input
- SDL_image / SDL_ttf
- miniaudio / WASAPI audio path
- chart parsing
- rhythm judgement and note progression
- character loading and animation
- Songs / Characters folder support
- Native save migration foundation
- Windows x64 build pipeline

The current Native gameplay engine is a foundation, not the final specification. When Native behavior differs from V1.14, V1.14 is the target.

## 5. Architecture

### 5.1 Hybrid Native + QuickJS model

Use a hybrid architecture:

- **C++ / SDL2** owns the application, rendering, input, audio, gameplay, files, persistence, timing, and scene lifecycle.
- **QuickJS** hosts browser-independent V1.14-compatible JavaScript logic where retaining original logic materially reduces parity risk.
- WebView2, Chromium, DOM rendering, Canvas rendering, and Web Audio are not reintroduced.

The intent is to preserve proven game logic without recreating a browser application inside the Native build.

### 5.2 C++ owns

- application lifecycle and main loop
- scene routing
- window and renderer
- input dispatch
- audio device and playback
- chart/gameplay execution
- note rendering and judgement presentation
- character rendering and animation
- Home / Halloween / Practice / Gameplay / Result presentation
- Songs / Characters / asset discovery
- Native save files and atomic-style disk writes
- diagnostics and logs
- QuickJS runtime lifetime and bridge

### 5.3 QuickJS owns

Only browser-independent compatibility logic required by Block 1, including as needed:

- 15,000-player population state transitions
- ONLINE / LIVE / WAIT calculations
- rest / sleep / activity state transitions
- persistent background/LIVE progression required by the Home population model
- title-screen pure calculations
- Halloween/event pure calculations required by Block 1
- pure song-difficulty/helpers required by population logic

V1.12 modules such as `population-social-sessions.js`, `title-system.js`, and relevant pure helpers are implementation references.

### 5.4 Browser dependencies explicitly forbidden

The compatibility runtime must not own or depend on:

- `document`
- DOM nodes
- browser UI lifecycle
- Canvas rendering
- `AudioContext` / Web Audio
- direct `localStorage`
- direct IndexedDB
- browser-owned timers for application state
- WebView2
- Chromium

Original JS code that expects those services must use a narrow Native bridge instead.

## 6. Core components

### `App`

Owns application lifecycle, the main loop, global time, scene routing, background-system advancement, and shutdown ordering.

Population internals and scene rendering must stay outside `App`.

### `TitleScene`

Reproduces the V1.14 Home/Title screen and reads real data from Native/compatibility state.

All V1.14 buttons are visible in their V1.14 positions. During Block 1 only completed Block 1 destinations are interactive; later-block buttons remain visually present but do not transition yet. Do not add Native-specific `COMING SOON` labels or redesign their disabled appearance.

### `HalloweenOverlay`

Reproduces the V1.14 event entry and Block 1 event presentation, including event availability, Candy, remaining time, and relevant summary state.

Heavy Shop/History content is constructed only when the corresponding overlay/subview is opened, preserving the performance intent of the current version.

### `PracticeScene`

Reproduces the V1.14 Practice flow:

- BF/DAD side selection where applicable
- song search
- star filtering
- song list and icons
- keyboard and mouse navigation
- launch of Native gameplay

### `GameSession`

Executes the selected chart and owns audio-synchronized gameplay state: judgements, combo, score, accuracy, HP, sustain behavior, song completion, and character animation triggers.

Existing Native GameSession behavior is corrected toward V1.14 when parity tests show differences.

### `ResultScene`

Reproduces the V1.14 Practice result flow and returns to Practice selection in the same way as V1.14.

Practice must not mutate RP or normal Online W/L/D records.

### `PopulationRuntime`

Owns QuickJS compatibility execution for Block 1. It:

- initializes compatibility modules
- advances world state independently of visible scene
- exposes compact typed snapshots to Native UI
- serializes/restores population state
- captures JS exceptions and reports them to Native diagnostics

It remains active during Home, Halloween, Practice selection, Gameplay, and Result.

### `SaveService`

Owns Native persistence and eligible V1.14 migration. It must never modify or delete the original V1.14 save source.

### `AssetService`

Centralizes Songs, Characters, icons, images, XML, and metadata discovery/caching, including missing/malformed asset handling.

### `UiRenderer`

Renders V1.14-equivalent widgets using SDL2 and logical V1.14 coordinates. It does not own game state.

## 7. Native/QuickJS bridge

The bridge must stay narrow and typed. It must not expose the entire Native application to JavaScript.

Conceptual API:

```text
population.advanceTo(now)
population.getSummary()
population.serialize()
population.restore(state)

save.get(key)
save.set(key, value)

songs.getMetadata(id)
```

Exact function names may change during implementation, but these rules are fixed:

- no DOM emulation layer
- no browser object graph
- no full 15,000-player transfer every frame
- no giant JSON round-trip for small hot-path values when typed structures are practical
- later screens request only the data they need

A Home population snapshot should be compact, for example:

```text
PopulationSummary
- registered
- online
- live
- liveCap
- waiting
- localPlayerState
- lightweight event summary
```

Later blocks may add paged ranking/spectator queries without changing the underlying population authority.

## 8. Time model

### 8.1 Real-time based, never FPS based

Population/event progression uses elapsed real time, not rendered frame count. A 144 FPS client and a 60 FPS client must not advance the simulated world at different speeds.

`App` advances the background runtime using the current clock.

### 8.2 Scene-independent progression

The population world keeps advancing while the player is in:

- Home
- Halloween overlay
- Practice selection
- Gameplay
- Result

Acceptance scenario:

- Home for 1 minute
- Gameplay for 3 minutes
- Result for 30 seconds
- return Home

The world must have progressed by 4 minutes 30 seconds.

### 8.3 Delays, sleep, and catch-up

If a frame stalls, elapsed time must not be silently lost. If the PC sleeps or the application resumes after a large time gap, use V1.14-equivalent catch-up/recovery semantics derived from the reference implementation rather than iterating frame-by-frame for hours or inventing a new approximation.

## 9. Save and persistence model

Use three conceptual levels:

1. **Hot state** — current RAM/QuickJS state
2. **Checkpoint state** — Native in-memory persistence candidate
3. **Disk state** — durable save files

Population changes do not cause disk writes per event or per frame.

Typical flush points include:

- safe time on Home
- Practice completion
- Result completion
- settings/event operations that require durability
- normal shutdown
- other V1.14-equivalent durable state boundaries

Important progress should update checkpoint state promptly even when disk flush is deferred.

Disk writes use an atomic-style pattern:

1. write temporary file
2. validate serialized content
3. flush as appropriate
4. replace/rename the durable target

A failed write must not replace a known-good save with a partial file.

## 10. V1.14 visual parity

### 10.1 Logical coordinate system

V1.14 presentation uses **1280×720 logical coordinates** as the rendering reference.

Native renders the same layout into that logical coordinate space, then scales the complete result uniformly to the physical window.

- 1920×1080 => 1.5× scale
- non-16:9 windows use letterboxing/pillarboxing as needed
- UI is not stretched or reflowed into a new layout

### 10.2 HTML/CSS as implementation reference

V1.12 embedded HTML/CSS supplies concrete measurements for layout, borders, shadows, gradients, padding, typography, and widget geometry where useful.

V1.14 visible behavior remains authoritative.

Do not introduce Native-specific colors, spacing, panels, labels, or UX restructuring.

### 10.3 Text and fonts

Use Windows/system fonts that match V1.14 `system-ui` behavior as closely as practical, including Japanese glyph support. Areas explicitly using fonts such as Consolas in V1.14 should preserve that intent.

Do not bundle arbitrary substitute font files solely to create a different Native look.

Small rasterization/anti-aliasing differences caused by the rendering stack are acceptable only when layout, metrics, and appearance remain otherwise faithful.

### 10.4 Character preview

Home character preview uses real animation data, not a static screenshot. It must use the same Character JSON/XML frames, offsets, scale, flip, and animation semantics as the gameplay asset path.

## 11. Practice and gameplay parity

Practice flow target:

```text
Home
 -> Practice overlay
 -> select side/search/filter/song
 -> Gameplay
 -> Practice Result
 -> Practice overlay
 -> Home when requested
```

Input meanings, including Enter/Esc and mouse actions, must follow V1.14 per-screen behavior.

Gameplay parity covers, at minimum:

- note spawn/despawn behavior
- scroll speed
- upscroll/downscroll behavior
- receptor position
- sustain length and judgement
- SICK / GOOD / BAD / MISS windows
- combo
- score
- accuracy
- HP changes
- ghost-tap behavior
- opponent note processing
- BF/DAD animation triggers
- idle return timing
- Character XML frame/offset behavior
- character flip and scale
- antialiasing behavior where supported
- HUD placement
- judgement popup behavior
- song completion conditions

The existing Native implementation is changed when required to match V1.14.

## 12. Parser and asset parity

For the same Song JSON, Native and V1.14 should agree on observable interpretation such as:

- note count
- sustain count
- BF/DAD assignment
- song duration/timing model
- BPM changes
- section interpretation
- difficulty
- star rating

For the same Character JSON/XML, Native and V1.14 should agree on:

- animation names
- frame sequences
- FPS
- looping
- offsets
- flip
- scale
- idle
- singLEFT / singDOWN / singUP / singRIGHT

V1.12 modules such as `chart-utils.js`, `character-utils.js`, and `song-difficulty.js` are implementation references for reproducing these semantics.

## 13. Halloween behavior

Block 1 must use V1.14 event semantics rather than a cosmetic skin.

The event timing and Developer override model are preserved, including Auto / Force On / Force Off behavior and explicit JST-based event boundaries.

Event state is real state, not a fake Home-only display.

Heavy event subviews are lazy-built when opened so title-screen updates do not rebuild expensive Shop/History content while hidden.

## 14. Error handling

### 14.1 Asset errors

Malformed/missing Song or Character assets must not crash the entire application if V1.14 would tolerate and skip/fallback that item.

Errors are isolated to the affected asset when practical.

### 14.2 QuickJS exceptions

On a compatibility-runtime exception:

1. catch the exception at the Native boundary
2. log subsystem/function/time and useful diagnostic state
3. retain the last known-good snapshot if safe
4. prevent corrupted compatibility state from being persisted
5. continue only when the affected subsystem can safely do so

Do not silently swallow errors that can corrupt state.

### 14.3 Save failures

A failed or invalid temporary save must not replace a valid durable save.

Original V1.14 migration sources remain untouched.

## 15. Testing strategy

### 15.1 Unit tests

Cover isolated logic including:

- chart parsing
- Character parsing
- star calculation
- event boundary calculations
- population state transitions
- save serialization/validation

### 15.2 Golden parity tests

Use fixed input, fixed clock, and seeded randomness to compare reference outcomes against Native/QuickJS outcomes.

Testability may inject clock/RNG dependencies, but production continues to use real clock and normal runtime randomness.

### 15.3 Visual parity tests

At 1280×720, capture representative Native states and compare them against V1.14 reference images for:

- normal Home
- Halloween Home
- Halloween overlay / relevant subviews
- Practice selection
- Gameplay idle
- Gameplay note hit
- Gameplay sustain
- Result

Font rasterization differences may use a narrow tolerance; layout, geometry, colors, spacing, and non-text artwork should remain strict.

### 15.4 End-to-end tests

Exercise:

```text
launch
 -> Home
 -> Practice
 -> play song
 -> Result
 -> back to Practice/Home
 -> close
 -> relaunch
```

Verify:

- population progression continued throughout
- save restored correctly
- Practice did not mutate Online RP/W-L-D
- event state remained correct
- no unexpected crash or state rollback occurred

### 15.5 Windows real-device verification

Passing automated tests does not alone establish completion. The resulting Windows x64 build must be launched and exercised on Windows hardware before the block is called complete.

## 16. Performance constraints

Block 1 must not reintroduce the periodic stutter problems that motivated the Native port.

Required constraints:

- do not copy all 15,000 player objects to C++ each frame
- do not run heavy population work in the audio callback
- do not perform disk I/O from note judgement/audio hot paths
- do not rebuild heavy Halloween Shop/History content while hidden
- do not intentionally cluster QuickJS GC into critical gameplay moments
- keep population simulation cadence separate from rendering FPS
- prefer compact snapshots and cached unchanged UI data

Performance fixes must not change V1.14-visible behavior to achieve speed.

## 17. Block 1 completion criteria

Block 1 may be called complete only when all of the following are true:

1. V1.14-equivalent Home is present at 1280×720 logical layout.
2. Halloween Home/event state uses real V1.14-equivalent rules and data.
3. The real 15,000-player population simulation is active from startup.
4. Population/LIVE/WAIT/rest/sleep-related Block 1 state continues while in Practice and Gameplay.
5. Practice selection is functionally and visually V1.14-equivalent for the supported Block 1 flow.
6. Gameplay observable behavior matches V1.14 for the tested parity surface.
7. Practice Result and return flow match V1.14.
8. Population/save state survives restart correctly.
9. Practice does not alter Online RP or normal Online records.
10. The V1.14 migration source is never modified.
11. Automated unit, golden-parity, visual-parity, and end-to-end tests pass.
12. Windows x64 build/package verification passes.
13. Windows real-device smoke testing is completed.
14. Remaining differences are documented and limited to accepted renderer-level micro-differences such as unavoidable font antialiasing, not behavior/layout differences.

A build that merely launches or resembles V1.14 is not Block 1 completion.

## 18. Intentionally incomplete after Block 1

These later systems remain visible where V1.14 shows their Home buttons, but their full functionality belongs to later blocks:

- Ranking / Record / Titles / full player-progress screens
- Online Battle / full matchmaking
- Spectate
- Friends
- Private Match
- Normal Boss
- Halloween Boss full gameplay flow
- Replay
- Settings beyond what Block 1 directly requires
- Discord Presence final parity

Their buttons must not be redesigned or removed simply because the destination is not yet ported.

## 19. Non-goals

Block 1 does not include:

- redesigning PKE for Native
- changing V1.14 gameplay rules for convenience
- replacing real population simulation with counters
- reducing the registered population for performance
- creating a new save ecosystem incompatible with later blocks
- restoring WebView2 as an implementation shortcut
- porting all six blocks in one change

## 20. Implementation principle

For each area, use the same sequence:

1. inspect the V1.12 embedded implementation and V1.14 observable behavior
2. define parity tests before changing production behavior
3. port or bridge the relevant logic
4. make the test pass
5. run regression tests
6. verify performance and persistence behavior
7. verify the Windows package and real-device behavior before claiming completion

The guiding rule is simple: **the implementation technology changes; PKE Beat Battle V1.14 should not.**
